# 微信云托管传输准备 / WeChat Cloud Hosting Transport Preparation

## 中文

小程序客户端现可在原有 HTTPS `wx.request` 与 `wx.cloud.callContainer` 之间选择，均调用现有 FastAPI `/v3` 接口，沿用服务器验证的微信登录、设备令牌、授权、加密存储、导出与删除。没有新增身份或健康数据链路。云托管私有链路无需在小程序后台配置请求域名，但并不自动完成后端部署、数据库、隐私审核或 iOS 访问。

云模式需要在公开配置中填写 CloudBase 环境 ID 与云托管服务名。若暂时没有生产 HTTPS 地址，可明确将 `baseURL` 留空，只通过 `wx.cloud.callContainer` 服务微信小程序；后端同时设置 `BODYOS_PUBLIC_AUTH_ENABLED=true`、`BODYOS_PRIVATE_WECHAT_CLOUD_ENABLED=true` 与空的 `BODYOS_PUBLIC_BASE_URL`。仅微信登录允许这种模式，Apple 登录与 iOS 配对继续拒绝，小程序也隐藏连接入口。将来配置真实生产 HTTPS 地址后，才可另行验收 iOS 连接。若填写 `baseURL`，仍必须通过生产域名校验。服务端还需安全配置微信 AppSecret、身份哈希密钥、数据加密密钥与持久数据库，绝不可写进小程序包。缺少环境 ID 或服务名时客户端拒绝请求；这些本地配置检查不证明账号已经开通、环境已绑定或服务已部署。

现有 `infra/tencent/Dockerfile.api` 包含 Feishu/Hermes/Codex 等生产组件，`compose.yaml` 将 API、worker、gateway 和 PostgreSQL 分开运行。根目录新 `Dockerfile` 则仅安装现有 FastAPI 包，保留迁移目录，并通过 `infra/tencent/cloudbase-api-entrypoint.sh` 强制生产、微信私有调用、独立 PG schema、持久数据库、有效的 32 字节加密密钥及关键服务端配置。执行 `python3 infra/tencent/prepare-cloudbase-api.py --output /tmp/fitcrew-cloudbase-api-<版本>` 可从**已提交且没有已跟踪改动**的工作树导出只含构建必需文件的目录，再把该目录作为 `tcb cloudrun deploy --source`；未跟踪与忽略文件不会进入打包目录，不得直接上传整个工作树。CI 已验证该暂存目录的 Docker 构建、API 导入与原有 Compose 冒烟测试，但没有云部署结果。要先取得账号下真实环境与计费信息，隔离部署 API 与持久数据库，验证备份恢复、登录/保存/重登/删除和真机体验，再上传提审。不得把已有东京 V2 服务当成新小程序已部署。

若选 CloudBase PostgreSQL 模式，必须新建该模式的环境；已有传统环境不能直接切换。官方权限说明指出，应用直连角色 `cloudbase_postgres` 不能执行 `CREATE TABLE` 等结构变更，需通过管理面 `ExecutePGSql`。默认 API 启动仍执行 Alembic；专用模式须同时设置 `BODYOS_DATABASE_SCHEMA=fitcrew` 和 `BODYOS_DATABASE_MIGRATION_MODE=verify-cloudbase-pg`，它只核对独立 schema 的表和版本，不执行迁移。仅设置 schema 而保留默认迁移模式会拒绝启动。在真实环境上先核验 schema 初始化、角色权限、TLS、备份恢复，再启服务。[环境模式](https://docs.cloudbase.net/quick-start/env-overview) · [PG 权限](https://docs.cloudbase.net/authentication-v2/auth/auth-pg) · [管理面 SQL](https://docs.cloudbase.net/database/postgresql/initialization)

`bodyos_api.cloudbase_pg_manifest.build_manifest()` 可从当前 SQLAlchemy 模型生成离线 JSON 清单：专用 `fitcrew` schema、按外键排序的表、索引、当前 Alembic 版本戳，以及撤销前端角色访问的语句。默认不授予任何服务端角色权限；只有明确传入安全的 `app_role` 才添加最小 DML 授权。该函数**不连接或执行数据库**。专用模式通过 SQLAlchemy 将 ORM 查询限定到 `fitcrew`，启动时只读检查表名、列名、索引、唯一约束、外键目标与版本号，缺失时拒绝启动；它不核对列类型、可空性、完整权限或真实业务闭环。生成清单不证明这些语句能在实际账号执行，也不提供生产连接配置、备份或回滚。应先核验全新空 schema、实际角色/网络/TLS、SQL 执行方式和可恢复性，再决定是否应用；绝不可对现有东京 V2 库运行。

后端现可选用腾讯云开发 AI 的服务端 HTTP 接口。私有云托管模式仅在服务器密钥配置 `BODYOS_CLOUDBASE_AI_ENV_ID`、`BODYOS_CLOUDBASE_AI_API_KEY` 和 `BODYOS_CLOUDBASE_AI_MODEL` 完整时才显示 AI 可用并允许单独同意；配置不全会禁用该 AI 能力，不会暗中切换到镜像中不存在的原有 CLI 服务商。仍须明确配置真实 `BODYOS_PRODUCT_AI_PROVIDER`、告知版本与单独同意，模型只接收既有脱敏摘要。模型名和可用性以实际账号控制台为准；本地测试没有验证账号的模型开通、费用或真实响应。官方接口和模型列表见[HTTP 调用](https://docs.cloudbase.net/ai/model/curl-access)与[可用模型](https://docs.cloudbase.net/ai/available-models)。

截至 2026-10-09：尚无环境 ID、服务名、实际公网地址、生产数据库、真机闭环或平台提审回执。微信开发者工具 CLI 当前返回 `islogin: false`，腾讯云 CLI 返回 `AUTH_FAILED`；需重新扫码并读取环境列表。腾讯云免费体验环境在小程序发布后第 15 天到期，不能作为长期免费正式服务；后续成本应在账号内按实际套餐核对。云托管私有调用和计费规则见[小程序访问云托管](https://docs.cloudbase.net/run/develop/access/mini)、[云托管服务设置](https://docs.cloudbase.net/run/deploy/service-setting)和[腾讯云价格文档](https://cloud.tencent.com/document/product/876/75213)。

微信优先私有调用只改变传输门槛。腾讯云[资源点价格说明](https://cloud.tencent.com/document/product/876/127357)写明：免费体验环境在小程序发布后第 15 天到期，不能支撑长期免费正式版。页面当前展示个人版优惠价每月 19.9 元，但账号所在地域、资格、结算价及超额费用仍需在购买前核对。若采用 CloudBase PG 加云托管，应选同时支持二者的地域；该价格表显示上海 PG 支持云托管，新加坡 PG 不支持。

## English

The private WeChat-first path changes transport requirements only. The [CloudBase resource-point pricing](https://cloud.tencent.com/document/product/876/127357) says the free trial expires on day 15 after Mini Program publication; it cannot support a lasting free release. The cited page currently advertises a 19.9 RMB/month personal plan, but the account's region, eligibility, actual checkout price, and overage need verification before any purchase. For a CloudBase PG plus Cloud Hosting deployment, use a region that supports both; the cited pricing table shows Shanghai supports Cloud Hosting with PG, while Singapore PG does not.

The Mini Program client can now select either its existing HTTPS `wx.request` transport or `wx.cloud.callContainer`. Both call the existing FastAPI `/v3` contract and preserve server-verified WeChat sign-in, device tokens, consent, encrypted storage, export, and deletion. No parallel identity or health-data stack is introduced. The private Cloud Hosting link does not require a Mini Program request-domain entry, but it does not deploy the backend, provision a database, complete privacy review, or provide iOS access by itself.

Cloud mode needs a CloudBase environment ID and Cloud Hosting service name in public configuration. Until a production HTTPS address exists, `baseURL` may explicitly remain empty and the Mini Program can use only private `wx.cloud.callContainer` calls. The backend must then set `BODYOS_PUBLIC_AUTH_ENABLED=true`, `BODYOS_PRIVATE_WECHAT_CLOUD_ENABLED=true`, and an empty `BODYOS_PUBLIC_BASE_URL`. Only WeChat sign-in accepts this mode; Apple sign-in and iOS pairing still refuse it, and the Mini Program hides the connection control. A real production HTTPS address and separate acceptance are required before iOS pairing can open. If `baseURL` is supplied, it must pass production-domain validation. Server-side WeChat AppSecret, identity pepper, encryption key, and durable database must remain protected and outside the Mini Program bundle. Missing environment ID or service name fails closed; local configuration checks do not prove account activation, linkage, or deployment.

The existing `infra/tencent/Dockerfile.api` includes Feishu/Hermes/Codex production components, while `compose.yaml` runs API, worker, gateway, and PostgreSQL separately. The new root `Dockerfile` installs only the existing FastAPI package and keeps migration files. `infra/tencent/cloudbase-api-entrypoint.sh` requires explicit production, private WeChat, isolated PG schema, durable database, a valid 32-byte field-encryption key, and server-side configuration. Run `python3 infra/tencent/prepare-cloudbase-api.py --output /tmp/fitcrew-cloudbase-api-<version>` from a worktree with **all tracked changes committed** to stage only required committed files, then use that directory with `tcb cloudrun deploy --source`. Untracked and ignored files never enter the stage; never upload the whole worktree. CI passed the staged Docker build, API import, and existing Compose smoke test; no cloud deployment has occurred. First inspect the real account's environment and billing, isolate the API and durable database, verify backup recovery and sign-in/save/relaunch/erasure on devices, then upload for review. The Tokyo V2 service is not evidence of deployment.

If CloudBase PostgreSQL mode is chosen, it requires a newly created PG-mode environment; an existing traditional environment cannot be switched. Tencent says the direct application role `cloudbase_postgres` cannot run structural DDL such as `CREATE TABLE`; schema changes use management-plane `ExecutePGSql`. Default API startup still runs Alembic. The dedicated mode requires both `BODYOS_DATABASE_SCHEMA=fitcrew` and `BODYOS_DATABASE_MIGRATION_MODE=verify-cloudbase-pg`; it checks the isolated schema's tables and revision without running migrations. Setting the schema with the default migration mode refuses startup. Verify schema initialization, role privileges, TLS, and backup recovery in the actual environment before serving traffic. See [environment modes](https://docs.cloudbase.net/quick-start/env-overview), [PG permissions](https://docs.cloudbase.net/authentication-v2/auth/auth-pg), and [management SQL](https://docs.cloudbase.net/database/postgresql/initialization).

`bodyos_api.cloudbase_pg_manifest.build_manifest()` now emits an offline JSON manifest from the current SQLAlchemy models: a private `fitcrew` schema, tables ordered by foreign-key dependencies, indexes, the current Alembic revision stamp, and client-role revocations. It grants no server role by default; an explicitly supplied safe `app_role` adds only DML privileges. The function **never connects to or executes against a database**. Dedicated mode maps ORM queries into `fitcrew` and checks table names, column names, indexes, unique constraints, foreign-key targets, and revision read-only at startup, refusing an incomplete layout. It does not validate column types, nullability, every privilege, or real user flows. A generated manifest does not prove that the actual account accepts those statements, nor does it configure the production connection, backups, or rollback. Verify a new empty schema, the actual role/network/TLS requirements, SQL execution method, and recoverability before applying anything; never run it against the existing Tokyo V2 database.

The backend can now optionally call CloudBase AI through a server-only HTTP API. In private Cloud Hosting mode it offers AI and permits separate consent only when `BODYOS_CLOUDBASE_AI_ENV_ID`, `BODYOS_CLOUDBASE_AI_API_KEY`, and `BODYOS_CLOUDBASE_AI_MODEL` are all set as server secrets. Missing or partial configuration disables the AI capability and never silently falls back to a CLI provider absent from this image. The actual `BODYOS_PRODUCT_AI_PROVIDER`, notice version, and separate user consent remain required; the model receives only the existing de-identified summary. Confirm model name, enablement, price, and actual response in the account; local tests prove none of those. See the official [HTTP API](https://docs.cloudbase.net/ai/model/curl-access) and [available models](https://docs.cloudbase.net/ai/available-models).
